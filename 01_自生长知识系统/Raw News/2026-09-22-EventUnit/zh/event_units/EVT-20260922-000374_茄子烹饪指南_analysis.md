# 数据治理中的来源一致性校验：以 Event Unit 生成失败为例

在构建自生长知识系统（如 748686 系统）时，**来源一致性校验（Source Consistency Check）**是确保事件单元（EventUnit）可信度的第一道防线。当路由（Router）根据元数据将文章归类至某一主题，而实际源文章内容与该主题严重不符时，系统必须触发熔断机制，而非强行合成。以下通过一例“标题与内容错位”的失败 Event 进行深入解析。

## 定义与解释

**来源一致性校验**是指在下发任务给各 Skill（如总结、扩写、笔记生成）之前，对 Event 标题与源文章内容进行语义匹配度检查的过程。其核心目标是防止**幻觉合成**（Hallucination Synthesis），即 AI 为了完成任务而强行连接不相关的信息源。
*   **应用场景**：新闻聚合、知识图谱构建、多源信息综合。
*   **关键指标**：语义相似度、主题关键词重叠率、上下文连贯性。

### 示例：成功校验 vs 失败校验
在成功案例中，若 Event 标题为“AI 融资”，源文章为“OpenAI 获新投资”，两者语义高度一致，系统可直接进入 Summarization Skill。
在失败案例（本 Event）中，标题为“茄子烹饪”，源文章为“软银发行债券”，语义完全正交。此时若跳过校验直接执行，将导致输出内容的彻底失效。

## 问题与答案

### Q1: 当发现源内容与 Event 主题不匹配时，系统应如何处理？
系统不应尝试“强行关联”，而应立即标记该 Event 为**数据异常**或**低质量**。在 EVT-20260922-000374 中，正确的处理方式是生成“来源不一致报告”，明确指出：Event 预期主题为烹饪，但源 ARTICLE #494 属于金融类。这种透明化处理比生成一篇错误的“茄子与软银关系”文章更有价值。它保留了数据的纯洁性，并为后续的再采集流程提供了明确的纠错信号。

### Q2: 如何量化“内容不匹配”的程度？
可以通过**交叉验证**机制来实现。首先，提取 Event 的核心实体（如：茄子、烹饪、低卡路里）和源文章的核心实体（如：软银、OpenAI、债券）。然后计算实体交集。在本例中，交集为空集。此外，还可以利用 LLM 进行零样本分类，判断源文章是否属于目标主题范畴。如果概率低于预设阈值（如 5%），则判定为不匹配。这种量化的手段可以避免主观判断的偏差，使系统能够自动化地拦截错误数据流。

### Q3: 缺乏源内容支持时，能否基于常识进行“补全”式生成？
**绝对不能**。这是知识工程中的红线原则——“绝不捏造事实”。在本事件中，虽然“茄子是低卡路里食材”是常识，但 Event Unit 的目的是基于**特定源文章**进行综合，而非进行通用知识科普。如果允许基于常识补全，系统将丧失作为“事实核查工具”的属性，退化为通用的聊天机器人。因此，当源文章缺失或错位时，输出应为“无法确定”或“数据缺失”，而非填充无关的正确知识。

## 步骤指导：事件质量控制工作流

当一个 Event Unit 被创建后，应按照以下步骤进行质量阻断与控制：

1.  **接收路由指令**：Router 固定选择 Skills（总结、扩写、笔记生成）。
2.  **源内容预检**：读取源文章列表，逐篇检查 Title 与 Body 的关联性。
    *   *动作*：在本案例中，检测到 ARTICLE #494 的内容为金融新闻。
3.  **主题匹配度评估**：将源文章内容摘要与 Event 标题进行语义比对。
    *   *判定*：匹配度极低，存在根本性冲突。
4.  **执行熔断与报告**：停止后续 Skill 的生成任务，生成“内容错位报告”。
    *   *输出*：明确列出 Event ID、预期主题、实际源主题、冲突详情。
5.  **触发再采集建议**：在 Event 结论中注明“建议重新采集相关可信源”，为后续人工或自动流程提供指引。

### 步骤细节示例
在执行第 4 步时，不仅要说“不匹配”，还要具体指出：“源文章提及 SoftBank 和 $11 billion，而事件主题涉及茄子和烹饪”。这种具体的反馈能帮助上层系统更精准地优化数据清洗管道，避免同类错误再次发生。

## 比较与对比：强行生成 vs 质量熔断

| 维度 | 强行生成 (Bad Practice) | 质量熔断 (Good Practice) |
| :--- | :--- | :--- |
| **事实准确性** | 低，可能产生幻觉或无关拼接 | 高，仅输出经过验证的事实或明确的状态标记 |
| **用户信任度** | 随时间下降，用户发现内容错乱 | 保持或提升，用户感知到系统的严谨性 |
| **资源消耗** | 浪费计算资源生成无用内容 | 节省资源，及时止损 |
| **后续处理** | 需要二次人工纠错 | 提供明确的纠错线索（如本 Event 的建议） |
| **典型案例** | 基于金融新闻硬写茄子食谱 | 输出“数据来源错误，无法生成指南” |

## 案例分析：EVT-20260922-000374 的治理启示

本 Event 是一个典型的**数据管道污染**案例。Event 标题由上游决定，源文章由爬虫或 RSS 拉取，两者在进入 Analysis Engine 前缺乏严格的对齐机制。
首先，系统识别出源文章 ARTICLE #494 的状态为 "unresolved" 且内容仅为摘要，这本身就是一个危险信号。其次，主题从“烹饪”突变为“金融”，揭示了元数据层面的标注错误。
这一案例表明，748686 系统不仅需要强大的 Generation Skills（生成技能），更需要强大的 **Sanity Check Skills（健全性检查技能）**。在没有有效源数据支持的情况下，任何扩写、总结或笔记生成都是无本之木。通过本案例的分析，我们确立了“源数据有效性优先于技能执行”的原则，这对于维护知识系统的长期价值至关重要。

## 理论与实践

从理论角度看，这符合**垃圾进，垃圾出（GIGO, Garbage In, Garbage Out）**的系统论原理。无论后端的 LLM 能力多么强大，如果输入的 EventUnit 基础数据是错误的，输出必然也是无效的。
在实践中，这意味着我们需要在 Router 阶段增加一个前置的**内容审计模块**。该模块不执行生成，而是执行验证。它负责回答一个问题：“这篇文章真的支持这个 Event 主题吗？”如果答案是否定的，整个流程应当在此终止，而不是盲目地调用“内容扩写大师”或“笔记生成器”。这种分层架构设计，既保证了生成质量的底线，又提高了系统的鲁棒性。
