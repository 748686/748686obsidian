## 1. 5Why 根因分析

### 🔴 问题描述
**当前现象**：事件引擎无法基于唯一来源（ARTICLE #366）合成关于“德国工资政策”的知识单元，导致事件状态标记为无效。
**影响范围**：知识图谱中“德国经济政策”节点缺失有效数据支撑；下游决策模型因缺乏此事件支持而中断。
**严重程度**：高（影响数据完整性与系统可信度）。

### 🔍 追问链条

**Why 1：为什么事件合成失败？**
**回答**：因为唯一引用的来源（ARTICLE #366）与事件主题完全无关。
**追问点**：为什么一篇关于足球比赛（沙尔克04 vs 柏林联合）的报道会被绑定到经济政策事件上？

**Why 2：为什么体育新闻会被关联到经济政策事件？**
**回答**：因为上游检索或匹配系统在处理该事件时，错误地获取或关联了不相关的条目。
**追问点**：为什么检索系统会出现这种跨领域的根本性错误？

**Why 3：为什么检索系统会产生跨领域错误匹配？**
**回答**：可能是检索关键词（如“力量/Power”、“温和/Moderate”等语义歧义）或ID映射错误（如`item-tech-news-366`的索引错位）导致的。
**追问点**：为什么在缺乏严格相关性校验的情况下，系统允许将`source_status: unresolved`且内容不符的来源锁定为唯一依据？

**Why 4：为什么系统缺乏严格的相关性校验机制？**
**回答**：因为当前的数据摄入流程假设“被检索到的文章必然相关”，缺乏基于语义一致性的自动过滤层（Semantic Consistency Filter）。

**Why 5：为什么流程设计中缺少一致性验证环节？**
**回答**：因为在系统设计初期，优先级侧重于数据吞吐量而非数据纯净度，且未将“来源可信度校验”作为默认阻断条件。

### 🎯 根本原因确认

## 2. 利弊分析表

**决策问题**：在面对“来源错误”时，系统应采取何种处理策略？

**选项对比**：

| 维度 | 选项 A：直接标记为 INVALID 并挂起 | 选项 B：基于错误来源强行生成“占位”知识 | 选项 C：自动触发重检索并替换来源 |
| :--- | :--- | :--- | :--- |
| **利处 1** | 保持数据纯净度，避免污染知识图谱。 | 维持事件ID的连续性，防止下游脚本因ID缺失报错。 | 自动化程度高，无需人工干预即可修复。 |
| **利处 2** | 明确标识系统错误，便于运维排查。 | 短期内维持系统表面运转。 | 快速响应，缩短数据延迟。 |
| **利处 3** | 符合“可追溯性”原则，记录失败原因。 | 看似完成了流程。 | 长期来看能积累更准确的数据。 |
| **弊处 1** | 该事件暂时无数据可用，下游应用需处理缺失值。 | 生成虚假或无意义的事实，严重降低系统可信度。 | 若重检索无结果，仍会失败，增加算力开销。 |
| **弊处 2** | 需要人工介入重新检索，效率较低。 | 一旦被发现，将导致全系统数据质量信誉崩塌。 | 依赖上游检索引擎的即时可用性。 |
| **弊处 3** | 用户可能暂时查不到该主题最新进展。 | 用户基于错误信息做出错误决策。 | 可能引入新的相关性错误。 |
| **推荐结论** | **🔹 选项 A (结合选项 C 的触发机制)** <br> 首先标记 INVALID，同时后台自动触发重检索。若重检索成功则更新，否则保持挂起。 | | |

**决策理由**：
1. **数据真实性优先**：选项 B 的红线不可触碰，错误合成比缺失更危险。
2. **鲁棒性**：选项 A 提供了安全网，选项 C 提供了修复路径。
3. **可逆性**：标记为 INVALID 是可逆操作，重新检索后可恢复；而错误合成难以清洗。

## 3. 情景规划

**规划主题**：知识系统数据源异常治理机制
**时间范围**：未来 3-6 个月

### 🎭 情景构建

#### 情景一：🌟 理想世界（自动化自愈）
**核心假设**：重检索引擎准确率高，语义过滤阈值设置合理。
**情景描述**：当 ARTICLE #366 这类错误匹配发生时，系统自动检测到低相关性，静默丢弃并触发重检索。30分钟内，系统获取了正确的“德国工资政策”文章，事件自动更新为 `VALID`。用户无感知。
**应对策略**：
1. 持续优化语义匹配模型权重。
2. 建立“静默重试”机制，允许最多 3 次自动重检索。

#### 情景二：📊 常态延续（人工介入混合）
**核心假设**：部分长尾主题检索困难，自动化命中率不稳定。
**情景描述**：类似“德国工资政策”的特定主题，自动重检索未找到高置信度来源。系统标记为 `PENDING_MANUAL_REVIEW`，数据运营团队每周处理一批此类挂起事件。数据完整性有 95% 的保障，但有 5% 的延迟。
**应对策略**：
1. 建立“待审队列”仪表盘，按主题分类。
2. 培训数据运营人员快速验证来源相关性。

#### 情景三：⚠️ 压力测试（上游检索服务降级）
**核心假设**：上游检索服务故障或返回大量噪音数据。
**情景描述**：大批量事件因来源不匹配而挂起。若系统盲目执行“选项 B”（强行合成），知识图谱将被垃圾数据淹没，导致下游所有决策模型失效。
**应对策略**：
1. **熔断机制**：当单日内 `INVALID` 事件占比超过 10% 时，暂停新的数据摄入。
2. **降级服务**：仅维持存量数据可用，停止增量更新。
3. **告警升级**：立即通知系统架构师检查检索接口。

### 🛡️ 鲁棒策略

1. **核心策略：来源-主题一致性网关**
   - 理由：无论上游检索质量如何，在数据入库前必须进行语义一致性校验。
   - 成本：增加 API 调用延迟（约 200ms）。
   - 收益：彻底杜绝“体育新闻绑定经济事件”这类荒谬错误。

2. **核心策略：分级数据可信度标签**
   - 理由：为每个事件标记 `Source_Confidence` (High/Medium/Low)。
   - 成本：增加元数据存储复杂度。
   - 收益：下游用户可据此决定是否信任该事件数据。
