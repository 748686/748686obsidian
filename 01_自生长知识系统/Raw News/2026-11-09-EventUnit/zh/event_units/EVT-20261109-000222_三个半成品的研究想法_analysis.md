## 常青笔记：信息溯源中的“已知缺失”处理原则

在构建自生长知识系统（如 748686 系统）时，处理“已知缺失”信息与处理“已知事实”同样重要。当原始数据源失效、内容被截断或仅存元数据时，如何准确记录这一状态而不产生幻觉或误导性推断，是知识工程师面临的核心挑战。本笔记旨在探讨在 Event Analysis 场景下，针对“信息真空”事件的标准化处理流程、评估标准及长期价值。

### 一、 定义：什么是“已知缺失”事件？

**“已知缺失”事件**是指在知识聚合过程中，系统识别到某个主题或标题的存在，但经过严格的多源验证后，确认无法获取其完整、可信内容的事实状态。这类事件通常具有以下特征：
1.  **标题存在性**：系统收到了包含明确标题的输入（如博客标题、新闻摘要标题）。
2.  **内容空洞性**：原始来源声明正文缺失，或者所有抓取到的内容仅为元数据（如日期、作者、URL失效提示）。
3.  **验证不可行性**：由于单一来源或所有来源均失效，无法通过交叉验证补全信息。
4.  **状态标记性**：在知识库中，该条目被明确标记为“unresolved”、“horizon_summary_only”或类似的状态，而非“completed”或“verified”。

例如，在 EVT-20261109-000222 中，标题为“三个半成品的研究想法”，但实际内容仅包含“Original URL: 未找到可信原文”等元数据。这是一个典型的“已知缺失”事件，其核心价值在于记录“曾有此话题，但内容不可得”，而非虚构内容。

**实际示例**：
假设在一个科技新闻聚合系统中，检测到一条标题为“量子计算机突破新纪录”的新闻。当系统尝试抓取原文时，发现所有镜像站点均已失效，且原始发布者已删除文章。此时，系统应生成一个“已知缺失”记录，注明“曾存在该新闻标题，但原文不可用”，而不是基于标题臆测量子计算机的具体突破点。这确保了知识库的纯洁性，避免了虚假信息的传播。

### 二、 解释：为何要严格区分“缺失”与“虚构”？

在知识管理和 AI 内容生成中，区分“缺失”与“虚构”至关重要，主要原因包括：
1.  **维护事实准确性**：知识系统的核心资产是可信度。如果为了填充知识库而编造缺失的内容，将导致系统产生“幻觉”，进而损害用户在决策时的信任。例如，若将 EVT-20261109-000222 中的“三个半成品研究想法”虚构为具体的 AI 算法，可能会误导后续的研究者。
2.  **避免污染数据链**：自生长知识系统依赖于上下层数据的传导。如果上游的“缺失”事件被错误地标记为“已验证事实”，下游的 Skill（如总结、笔记生成）将基于错误的前提进行二次创作，导致错误知识的指数级扩散。
3.  **明确检索意图**：用户搜索“三个半成品的研究想法”时，如果系统返回的是虚构内容，将严重误导用户。相反，如果系统返回“该话题存在，但原文缺失，仅记录如下元数据”，则提供了诚实且有用的信息。
4.  **符合伦理规范**：在学术和专业技术领域，引用不存在或未证实的信息被视为学术不端。AI 系统作为知识助手，必须遵循同样的伦理标准，不编造不存在的信息。

**应用场景**：
在学术研究支持系统中，当研究者查询某个小众学者的早期论文时，如果该论文已失传，系统应清晰标注“论文失传，仅存引用记录”，并提供相关引用文献的线索，而不是生成一篇“疑似论文内容”。这不仅保护了研究者的时间，也维护了学术记录的严肃性。

### 三、 示例： EVT-20261109-000222 的处理流程分析

以 EVT-20261109-000222 为例，展示如何对一个“已知缺失”事件进行标准化处理：

1.  **接收与初筛**：系统接收来自 Horizon 日报的摘录，标题为“三个半成品的研究想法”。Router 固定选择“总结文章.md”和“笔记生成器.md”两个 Skills。
2.  **来源验证**：Event Analysis Engine 检查 ARTICLE #23，发现其明确声明“Original URL: 未找到可信原文”且“Horizon 摘要不会被视为原文”。
3.  **事实确认**：引擎确认没有任何技术细节可供提取。此时，策略从“内容总结”调整为“元数据记录”。
4.  **Skill 执行**：
    *   **总结文章.md**：没有实质内容可总结，因此生成的摘要聚焦于“描述缺失状态”，列出已知的时间、标题、来源标记和验证结果。
    *   **笔记生成器.md**：生成关于“如何处理信息缺失”的常青笔记，而非虚构研究想法。笔记内容围绕“已知缺失”的定义、重要性及处理原则展开。
5.  **输出与标记**：最终输出被标记为“待处理”或“unresolved”，并明确告知用户“不得将此标题解读为已发表的技术成果”。

**具体操作细节**：
在总结阶段，必须列出“无法确定”的清单，如作者身份、技术可行性、原始出处等。在笔记生成阶段，应选择“问题-答案”或“步骤指导”结构，解释“当遇到来源缺失时，AI 应如何做”。例如，步骤一：验证来源有效性；步骤二：检查多源交叉验证可能性；步骤三：若均失败，生成“缺失记录”而非“虚构内容”。

### 四、 常青笔记的表达结构应用

为了更全面地阐述“已知缺失”事件的处理原则，本笔记采用以下三种表达结构：

#### 1. 问题-答案结构：关键决策点

**Q1: 当所有来源都失效时，是否可以用 AI 推断出大致内容？**
A1: 绝对不可以。在 Event Analysis 的严格契约下，AI 不得编造任何不存在的信息。即使根据标题和元数据可以推测主题领域（如“技术博客”、“研究构想”），也不能虚构具体的论点、数据或结论。正确的做法是明确记录“内容缺失”，并标记为“unresolved”。推断会引入噪音，破坏知识系统的可信度。

**Q2: “已知缺失”事件是否应该被从系统中删除？**
A2: 不建议直接删除。这些事件具有“元数据价值”，它们记录了信息的曾经存在和当前不可得状态，是知识图谱完整性的一部分。删除会导致历史记录的断裂。正确的做法是将其保留，但明确标记为“缺失记录”，并链接到相关的“信息溯源”或“数据质量控制”常青笔记。

**Q3: 如何判断一个事件是“缺失”还是“未充分提取”？**
A3: 需要通过严格的 Source Verification 步骤。如果尝试了所有可用的 Source（包括镜像、归档、关联引用）后仍无法获得正文，则判定为“缺失”。如果仅仅是当前抓取失败但有其他来源佐证，则应标记为“待补充”而非“缺失”。在 EVT-20261109-000222 中，由于只有一个来源且该来源自认失效，故判定为“缺失”。

#### 2. 步骤指导结构：处理“信息真空”的标准流程

**步骤一：验证来源的有效性与完整性**
首先，检查所有输入来源的 `source_status` 和 `content_status`。如果状态标记为 `unresolved`、`horizon_summary_only` 或 `url_not_found`，则进入下一步。确保已经尝试了多源交叉验证，如果仅有一个来源且该来源声明内容缺失，则确认信息真空。

**步骤二：提取可用的元数据**
即使正文缺失，元数据（如标题、日期、作者标记、来源平台）仍然有价值。详细记录这些信息，作为“缺失记录”的核心字段。例如，记录 EVT-20261109-000222 的日期、标题、来源 ARTICLE #23 的评级 (?/10) 和状态标记。

**步骤三：生成“缺失记录”而非“内容总结”**
调整 Output 策略。不要尝试生成虚假的内容摘要。相反，生成一份报告，说明“标题为 X 的内容存在，但经验证，原文不可用，目前仅存以下元数据”。明确列出“已知缺失”的项目，如具体内容、作者身份、技术结论等。

**步骤四：关联至“知识质量控制”常青笔记**
为该事件生成相关的常青笔记链接，如“信息溯源原则”、“AI 幻觉防范”、“元数据记录标准”等。这有助于后续研究者理解为何该事件未被正常处理，以及系统在此类情况下的决策逻辑。

**步骤五：标记为“待处理”并等待后续**
在系统中将该 EventUnit 的状态保持为 `pending` 或 `unresolved`，并添加注释说明“等待后续 AI 二次处理及 27 Skills 分析”或“等待来源补充”。这确保了未来如果有新的来源出现，系统可以重新触发处理流程。

#### 3. 比较与对比结构：“缺失记录” vs “虚构内容”

| 特性 | 缺失记录 (Known Missing) | 虚构内容 (Fabricated Content) |
| :--- | :--- | :--- |
| **事实基础** | 基于真实存在的元数据（标题、日期、来源标记） | 基于 AI 的推测、幻觉或编造 |
| **可信度** | 高（诚实反映当前知识边界） | 极低（一旦被发现，系统性信任崩塌） |
| **用户价值** | 高（告知用户“查不到”，避免误导） | 负价值（提供错误信息，浪费用户时间） |
| **系统影响** | 维护数据纯洁性，便于后续追溯 | 污染知识图谱，导致错误扩散 |
| **处理策略** | 标记为 `unresolved`，保留元数据 | 应被严格禁止，需通过提示词约束防止 |
| **示例** | EVT-20261109-000222：记录“原文未找到” | 虚构“三个研究想法是 A, B, C” |
